# Генератор текстов

На входе: **GEO**, **список ключей**, **конкуренты**. На выходе: проверенный текст в `.txt` (+ JSON для импорта в AffBulk).
Каждый шаг сохраняет результат в папку запуска `runs/<ключ>-<geo>/`, и следующий шаг читает параметры оттуда.

## Установка

```bash
pip install -r requirements.txt
copy .env.example .env      # и вписать ANTHROPIC_API_KEY
```

## Запуск

Файл входных данных (`input/vegashunter.txt`) — в том же формате, что в задаче:

```
GEO - Australia
Keywords - VegasHunter, Vegas Hunter, VegasHunter casino
Competitors:
https://vegashunters-au.com/au/
https://vegas-hunter.org/
```

(можно и JSON: `{"geo": "...", "keywords": [...], "competitors": [...], "language": "en", "facts": [...]}`;
`language` по умолчанию определяется по GEO, `brand` — название бренда (по умолчанию первый ключ), `facts` — «информация о бренде»: **единственный источник фактов о бренде** (лицензия, бонусы, платёжки, провайдеры, сроки). В текстовом формате: строки `Brand - ...` и `Facts - ...` (можно несколько). Без `facts` текст получится общим, без конкретики.)

### Тип страницы (`Page type`)

Один и тот же пайплайн (шаги 1–4) умеет три типа страниц. Тип задаётся строкой `Page type - ...` (в JSON: `"page_type"`); без неё — `brand-review`, как раньше.

| Тип | Что за страница | Ввод | База знаний | Что отличается |
|---|---|---|---|---|
| `brand-review` (по умолчанию) | общий обзор одного бренда (главная) | `Brand` — по желанию (по умолчанию первый ключ) | одна, вся используется | таблица фактов 2-м/3-м блоком, каждый блок со ссылкой на базу, **все** переменные базы использованы |
| `brand-subpage` | одна тема одного бренда: App, Login, VIP Program, Sports, Bonuses & Promo Code, Payments | **`Brand` обязателен** (первый ключ называет тему: «Longfu88 login») | одна, используется **нужная теме часть**: не менее половины блоков со ссылками, остальные переменные могут не использоваться | нет таблицы фактов; чужие для темы обязательные кластеры конкурентов можно пропустить (`skipped_clusters` с причиной, не больше половины); писатель не пересказывает бренд |
| `top-list` | рейтинг нескольких казино («best online casinos», «fast withdrawal casinos», «Kasyna bez weryfikacji») | список `Casinos:`, бренда нет | **по базе на каждое казино** | таблица сравнения 2-м/3-м блоком, отдельный раздел на каждое казино **в порядке ввода** (порядок = рейтинг), факты казино не смешиваются, оценок и «лучший» без данных нет |

Формат ввода для топ-листа (порядок казино = порядок рейтинга; примеры в `input/examples/`):

```
GEO - PL
Language - pl
Page type - top-list
Keywords - kasyna bez weryfikacji, kasyno bez weryfikacji
Casinos:
- Incaspin | incaspin-new
- Longfu88 | longfu88-new
Competitors:
https://planetagracza.pl/kasyno-bez-weryfikacji/
```

(`Casino - Имя | база` в одну строку тоже работает; в JSON — `"casinos": [{"name": "...", "knowledge_base": "..."}]`.) Базы казино Claude Code сохраняет **по одной**: `runs/<run>/00_kb/<slug казино>.json` (формат тот же, что `00_knowledge_base.json`; слаг — имя латиницей через дефис: `Long Fu 88` → `long-fu-88`). Пути в `kb_refs` начинаются со слага: `incaspin.brandinfo_welcome.welcome_bonus.total_bonus`. В запрос шага 1 значения баз попадают сокращёнными (`kb.digest`), в ТЗ код подставляет полные значения по пути.

Для каждого типа свои промпты: `prompts/step1_brief_<тип>.md`, `step1_review_<тип>.md` (шаг 1), `writer_<тип>.md` (дописывается к `system_prompt.md` на шаге 2), `step3_consistency_<тип>.md` (дописывается к проверке шага 3). Для `brand-review` ничего не меняется. Варианты ТЗ (`variants`) и импорт в AffBulk (`affbulk/`) рассчитаны только на `brand-review`.

### База знаний AffBulk (информация о бренде)

В файл входных данных добавляется строка `Knowledge Base - <название базы в AffBulk>` (в JSON: `"knowledge_base"`), пример: `input/incaspin.txt`.

- **Выбор базы** (шаг 0): Claude Code находит её в AffBulk через MCP (`knowledge_bases_find`, по названию) и сохраняет в `runs/<run>/00_knowledge_base.json` (Python сам MCP вызвать не может). Если база названа, но файла нет или название не совпадает, шаг 1 останавливается с понятной ошибкой, молчаливой подмены нет.
- **В ТЗ** для каждого блока указываются пути в базе (`kb_refs`), а код подставляет **значения дословно** (`Brand Information` в `01_brief.md`, поле `brand_info` в `01_brief.json`). Модель значения не переписывает. Код проверяет: пути существуют, у каждого блока есть данные, **все переменные базы использованы**.
- **На шаге 2** блок получает свою `Brand Information` как единственный источник фактов о бренде; шаг 3 проверяет текст на совпадение с этими фактами.
- **Подводные камни, которые код ловит:** если в факте базы есть бренд (`incaspin.com`, «Incaspin Originals», `support@incaspin.com`), он засчитывается как ключ. Такой блок получает «Counting warning», а в ТЗ прописывается, как перефразировать. Противоречия внутри базы (например, коды INC2/INC3 против «промокод не нужен») решаются в `copywriter_notes`, писателю решать нечего.

- **Таблица фактов о бренде** (обязательна, если есть база знаний): короткая таблица «параметр | значение» (компания, лицензия, год запуска, языки, валюты, платёжные системы, приветственный бонус, кешбэк, мин. депозит, e-mail поддержки) стоит **2-м или 3-м блоком** страницы, как «Casino Information» у конкурентов. Шаг 1 собирает такие таблицы у конкурентов (`01_fact_tables.json`) и выбирает строки по ним; обязательны licence, welcome_bonus, cashback, currencies, languages, payment_methods, support. Значения строк берутся из базы знаний по `kb_refs` строки и подставляются кодом дословно; писатель сокращает их до коротких фактов (≤ 25 слов), шаг 3 проверяет число строк и длину значений. Если значение содержит ключ (e-mail `support@incaspin.com` → «Incaspin»), блок таблицы обязан заложить это вхождение. Без базы знаний шаг 1 печатает предупреждение, и таблица не добавляется.

```bash
python -m textgen run input/vegashunter.txt        # весь пайплайн, шаги 1 → 4
python -m textgen step1 vegashunter-australia      # или отдельные шаги: step1 | step2 | step3 | step4 | loop
python -m pytest tests                              # тесты (без обращения к API)
```

Опции `run`: `--words 2500` (задать объём вместо медианы конкурентов), `--html-dir <папка>`, `--force` (пересобрать ТЗ), `--force-final` (сохранить txt, даже если проверки не пройдены).

## Что делает каждый шаг

| Шаг | Что происходит | Что сохраняется в `runs/<run>/` |
|---|---|---|
| **1. Анализ конкурентов** | Скачивает страницы, считает вхождения ключей в тексте и в H1–H6 (код). Кластеризует H2–H6 по смыслу (LLM), частота и средний объём секции считаются кодом; «обязательные» = встречаются минимум у 2 конкурентов (и ≥ 50 % от загруженных страниц). Код также собирает кандидатов в сущности (названия из текстов конкурентов). LLM строит ТЗ по образцу: **диапазон слов**, **ключи и их точное количество**, **Entities to cover [приоритет 1–10]**, **Entity Connections**, **Summary**, **Visual Elements**, **Copywriter Notes**, формат (параграфы / список / таблица). У родительских заголовков показывается и сумма «включая подразделы». Код проверяет ТЗ (уровни H, суммы слов и ключей, покрытие обязательных), LLM проверяет согласованность и исправляет | `01_competitors_raw.json`, `01_keyword_stats.json`, `01_heading_clusters.json`, `01_entity_candidates.json`, `01_fact_tables.json` (таблицы фактов конкурентов), **`01_brief.json`**, `01_brief.md` (читаемое ТЗ) |
| **2. Генерация** | ТЗ режется на блоки (1 заголовок = 1 вызов), каждый блок пишется с **вашим системным промптом**; в сообщение идут параметры блока, outline и уже написанные блоки (для согласованности). Затем сборка | `02_blocks.json`, `02_text_draft.md`, `02_history/iter_NN.json` |
| **3. Проверка** | Код: объём блока, точное число ключей, язык (langdetect + проверка алфавита), формат. LLM: согласованность и последовательность. Все находки сводятся в **один набор правок по блокам** → шаг 2 перегенерирует только эти блоки → проверка повторяется (до 4 итераций) | `03_check_iter_NN.json`, `03_fixes_iter_NN.json` |
| **4. Сохранение** | Только если шаг 3 пройден | `04_final.txt`, `04_final.json`, копия в `output/<run>.txt` |

## Важные правила подсчёта

- **Ключи**: без учёта регистра, только целые слова, **самое длинное совпадение первым**: «VegasHunter casino» считается только как «VegasHunter casino», а не ещё и как «VegasHunter». Поэтому счётчики ключей независимы.
- Ключи в ТЗ задаются на **тело блока**; ключи внутри самих заголовков учитываются отдельно, и сумма «тела + заголовков» по каждому ключу равна цели на весь текст.
- Цель по объёму и ключам = **медиана конкурентов** (плотность ключей ограничена 4 % от объёма, чтобы не копировать переспам).
- **Размерные группы конкурентов и лимит текста** (`python -m textgen tiers <run> --texts 8` покажет их). Тексты конкурентов делятся по естественным разрывам на малые, средние и большие (Login: 238·385·524 | 844 | 1754; longfu88-sg: 1116·1473 | 1836·1957 | 3355). Цель группы — её среднее, лимит — среднее × 1,2 (малая, средняя) или × 1,0 (большая; такой текст может быть короче лимита, если фактов не хватает). Базовое ТЗ строится по средней группе, малые варианты урезают его (важные блоки, минимум сущностей и фактов), большой дополняет блоками и фактами. Одиночный выброс в большой группе получает 1 текст на 10 текстов (но не меньше одного). Лимит пишется в ТЗ и проверяется на шагах 1 и 3. Блок растёт под свои факты не более чем на +20 % (в ТЗ), при генерации может выйти за максимум ещё на +10 %. Вес для расчёта: связь сущностей — 15 слов, сущности слов не получают, факт базы — по длине значения (число или название от 3 слов, предложение 10–20, максимум 30; список или таблица — слова самих пунктов). Не помещается — режем факты и связи или подаём коротким списком/таблицей.
- Объём блока — **ровно диапазон из ТЗ** (например 132–168 слов; диапазон строит ТЗ около ±12 % от середины), ключи — точное совпадение.
- Формат: недостающий формат — ошибка; лишние список/таблица — ошибка; один вводный/завершающий абзац рядом со списком или таблицей допускается.

## Настройка

- **Системный промпт** → `prompts/system_prompt.md` (собран из `prompts_base/1.txt` и `Prompt-rewriting.txt`; описывает ровно те секции, которые шаг 2 отправляет в запросе: CONTEXT, PAGE STRUCTURE, ALREADY WRITTEN BLOCKS, BLOCK BRIEF, FIX MODE). Правки вносите в этот файл.
- Промпты анализа и проверок → `prompts/step1_*.md`, `prompts/step3_consistency.md`.
- Допуски и модели → `.env` (см. `.env.example`).
- Без API-ключа: `--llm manual` — запросы к модели пишутся в `runs/<run>/llm/*.request.md`, ответы читаются из `*.json` (так шаг 1 был выполнен для текущих запусков).

## Если сайт конкурента не скачивается (403 / Cloudflare)

Сохраните страницу из браузера как `input/html/<домен>.html` (например `input/html/vegashunters-au.com.html`) — она будет использована вместо скачивания. Если сайт не загрузился и файла нет, шаг 1 продолжит с остальными конкурентами.


## Язык брифа и заголовки страницы

- **Бриф (ТЗ) всегда на английском**, какой бы ни был GEO: интент, заголовки блоков, Summary, Copywriter Notes, сущности и связи. Проверка кода отклоняет бриф с немецким/польским и т. п. текстом (для коротких заголовков надёжно ловится только диакритика, остальное проверяет ревью). `01_brief.md` тоже на английском.
- **Заголовки самой страницы на языке GEO.** Шаг 2 начинается с локализации заголовков (`02_headings.json`): модель переводит английские рабочие заголовки по-человечески (не дословно) и **сохраняет ровно те ключи, которые ТЗ запланировало в заголовке** (`heading_keywords`). Код проверяет число ключей и язык, при ошибке просит переделать только плохие заголовки. Шаг 3 перепроверяет их, шаг 4 собирает текст с локализованными заголовками, в `04_final.json` лежат оба варианта (`heading`, `heading_en`).
- Отдельный запуск: `python -m textgen headings <run>`. Для английских страниц локализация не нужна.
- В запросе на генерацию блока писатель видит английский рабочий заголовок и локализованный заголовок страницы; сущности даны по-английски, писатель выражает их стандартными терминами языка страницы.



## Варианты ТЗ (уникализация на уровне брифа)

Одинаковые вводные дают одно и то же ТЗ (медианы конкурентов, один набор блоков), поэтому 10-20 разных текстов нельзя получить простым перезапуском. Шаг 1 (анализ конкурентов, база знаний) выполняется **один раз**, а из его ТЗ собираются варианты:

```bash
python -m textgen variants input/variants/incaspin-pl.json            # собрать все варианты → runs/incaspin-pl-v01 … v05
python -m textgen variants input/variants/incaspin-pl.json --only v02 # один вариант
python -m textgen compare input/variants/incaspin-pl.json             # отчёт о различиях → output/incaspin-pl-variants.md
```

`input/variants/<имя>.json` (чертёж) задаёт для каждого варианта: порядок блоков (объединение, разделение, новые блоки), заголовки, размеры, форматы (проза/список/таблица), распределение ключей, приоритеты сущностей, строки таблицы фактов, выбор примеров игр и провайдеров, голос и угол страницы (`intent_summary`). `textgen/variants.py` собирает из чертежа настоящие блоки ТЗ, наследуя от базового ТЗ всё, что должно оставаться верным: значения базы знаний дословно, решения конфликтов в `copywriter_notes`, обязательные кластеры, использование всех переменных базы, таблицу фактов 2-м или 3-м блоком. Фразы про число ключей в заметках пересоздаются из итоговых чисел. Итог проверяется той же `validate`, что и шаг 1, а затем размер блоков пересчитывает `apply_coverage_budget`.

Каждый вариант лежит в своей папке запуска (`runs/<база>-vNN/`, копии артефактов шага 1 + `01_brief.json`, `01_brief.md`, `01_variant.json`), поэтому шаги 2-4 и импорт в AffBulk работают с ним как с обычным запуском (`python -m textgen headings incaspin-pl-v03`, затем `step2`, `loop`, `step4`).
