## 2. Логика

### 2.1 Поток данных
```
ТЗ блока (01_brief.json) ─┐
база знаний → brand_info ─┤→ step2.build_user_message → [system_prompt.md + user message] → LLM → clean_output → 02_blocks.json
уже написанные блоки ─────┤                                                                      │
FIX-список из шага 3 ─────┘                                                                      ▼
                                                                          шаг 3: детерминированные проверки + LLM-ревью → fixes → снова шаг 2
```
Системный промпт **статичен** и не содержит данных: все цифры, ключи и факты приходят в user message. Поэтому промпт описывает правила, а не контент.

### 2.2 Иерархия решений (секция 3)
1. Жёсткие ограничения ТЗ: язык, диапазон слов, точные счётчики ключей, форматы.
2. Целостность фактов: ничего не выдумывать и не обещать.
3. Покрытие: summary, все сущности (чем выше приоритет, тем раньше и больше места), все связи.
4. Польза читателю и согласованность со страницей.
5. Естественный стиль.

Правило сброса: стилистическое пожелание, которое мешает пунктам 1–3, отбрасывается. При нехватке места первыми урезаются сущности с низким приоритетом.

### 2.3 Логика фактов (секция 4)
- Бренд-факт можно писать, только если он есть в `Brand Information` блока или в `facts` контекста.
- Числа, суммы, проценты, названия переносятся **дословно**. Меняется только локальное форматирование (`€2,750` → `2.750 €`).
- Нет факта: безопасная общая формулировка или «not specified» (переведённое) в ячейке таблицы.
- Конфликт значений в базе: выполнить `Copywriter Notes`; если они молчат, взять более осторожное значение и опустить спорную деталь. О конфликте в тексте не упоминать.
- Сущность из ТЗ не доказывает, что она есть у бренда. Платёжку, провайдера или регулятора можно назвать «своими» только при подтверждении в базе.
- Лицензия и легальность в ГЕО: называть только то, что дано, и не утверждать «легален в ГЕО».

### 2.4 Логика ключей (секция 5)
- Подсчёт без учёта регистра, по целым словам, **самое длинное совпадение первым**: вхождение «X casino» не считается ключом «X».
- Ключ вставляется дословно, без склонения и перестановки. Предложение строится вокруг него.
- Бренд и все его написания тоже ключи. При лимите 0 бренд нельзя писать нигде: ни в списках, ни в заголовках таблиц, ни внутри длинной фразы.
- Бренд прячется в фактах (`incaspin.com`, `support@…`, «Incaspin Originals»). Тогда приходит «Counting warning» и нужно перефразировать.
- Нельзя выделять ключи кавычками или жирным ради счётчика, нельзя сгущать их в одном предложении.

### 2.5 Покрытие и формат
- Сущности: приоритет 8–10 идёт раньше, называется стандартным именем и получает больше места. Приоритет 1–3 получает клаузу или пункт списка.
- Связи `A → отношение → B` формулируются явным предложением или строкой таблицы.
- Допустимы три элемента: paragraph, list (без вложенных), table (шапка + разделитель). Всё остальное запрещено: `#`, HTML, hr, bold/italic (кроме явной просьбы в notes), эмодзи.

### 2.6 Цикл исправления (секции 12–13)
Блок падает на проверках → в user message добавляется `## FIX MODE` с текущим текстом и списком проблем → модель переписывает блок **целиком**, выполняя числа буквально («3 вхождения, нужно 1» → убрать ровно два) и перепроверяя остальные ограничения (сокращение может убить ключ или сущность).

## 3. Где промпт раздут

Один и тот же запрет повторяется в 2–3 местах. Это и есть основная часть 16 тысяч знаков.

| Повтор | Где встречается |
|---|---|
| «Не повторять содержимое других блоков» | 2, 6, 11 |
| «Не выдумывать / не обещать выигрыш / не risk-free» | 4 и 10 (hype) |
| «Сущность из ТЗ ≠ факт о бренде» | 4 и 6 |
| Бренд при лимите 0 и бренд внутри фактов | 4 и 5, плюс «Counting warning» из `step2.py` |
| Диапазон слов | 3, 7, 13 |
| Fix mode | 12 и текст секции `## FIX MODE`, которую `step2.py` добавляет сам |
| Нет заголовков и комментариев | 8 и 14 |
| Чек-лист самопроверки | 13 пересказывает пункты 4–10 |
| Объяснение структуры входа | 2 дублирует то, что и так видно из заголовков user message |

Задачи, которые лучше выполняет код, чем промпт: подсчёт слов и ключей (`textutil.py`), структура формата (`analyze_format`), фиксы по числам (шаг 3). Промпт тратит на них около 3,5 тыс. знаков (секции 5, 7 и часть 8), хотя проверка и так детерминированная.

### Более радикальный вариант: ядро + модули
Сейчас шаг 2 грузит один файл. Если разделить промпт на модули и подмешивать их по условию:

- **Ядро (всегда)**: ROLE, PRIORITIES, FACTS (сжатые), KEYWORDS (сжатые), LANGUAGE, OUTPUT. Около 5 тыс.
- **+ формат** только для блока с `table` (правила таблиц) и только для `list` (правила списков).
- **+ ENTITIES** только если у блока есть связи.
- **+ STYLE-чёрный список** остаётся, остальное в ядре.
- **+ FIX MODE** только в вызовах с `fixes`.
- **+ Counting warning** уже подмешивается кодом (`brand_info_hazards`).

Итог: обычный блок получает ~6–8 тыс., fix-вызов ~7–9 тыс. Это требует правки `prompts.py::load_writer_prompt` и теста `test_real_system_prompt_is_in_place`. Тест сейчас проверяет, что в системном промпте упомянуты все пять `##`-секций user message, поэтому их названия в ядре надо оставить.

## 5. Замечания по содержанию

1. **Старый шаблон в `prompts_base/1.txt` устарел.** Он выдаёт HTML (`<h2>`, `<p>`) и пишет заголовок сам, а текущий промпт выдаёт Markdown-тело без заголовка. Если часть пайплайна ещё читает `prompts_base/`, формат вывода разойдётся.
2. **Противоречие в STYLE.** «Начни с самой полезной информации» и «короткий hook в интро допустим» соседствуют без приоритета. Лучше сказать прямо: hook только если в ТЗ есть блок-введение.
3. **Размытое «Grade Level 7–8».** Модель не может его измерить. Конкретнее: «средняя длина предложения до ~18 слов».
4. **Запрет em dash и точки с запятой** в чёрном списке стиля. Это дешёвая детерминированная проверка, её лучше перенести в `checks.py` и убрать из промпта.
5. **Чёрный список слов** (около 40 позиций) можно хранить в коде и подставлять в fix-вызов только при нарушении. В основном промпте хватит 8–10 самых частых.
