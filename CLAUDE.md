# Генератор текстов — заметки для Claude

Проект: генерация SEO-текстов по ключам/GEO/конкурентам (Python-пакет `textgen`) и последующий импорт в AffBulk через MCP.
Подробности пайплайна — в `README.md`.

## Правила
- Каждый шаг пишет результат в `runs/<run>/` и следующий шаг читает его оттуда; не передавай данные между шагами в обход файлов.
- Подсчёт слов/ключей/форматов — только через `textgen/textutil.py` (одни и те же функции в шаге 1 и в проверках шага 3).
- Системный промпт лежит в `prompts/system_prompt.md` (собран из `prompts_base/`); если в нём снова появится `TEXTGEN_STUB_PROMPT` — шаг 2 не запустится.
- ТЗ-блок содержит: `words_min/words_max`, `keywords` (точные числа на тело блока), `entities` и `entity_connections` с приоритетами, `summary`, `copywriter_notes`, `formats`. Схема — `textgen/brief.py`; сообщение для шага 2 собирает `textgen/step2.py`, и оно должно соответствовать секциям `prompts/system_prompt.md` (это проверяет тест).
- **Весь бриф всегда на английском, независимо от GEO**: `intent_summary`, `heading`, `summary`, `copywriter_notes`, названия сущностей и связей. Код это проверяет (`validate` в `textgen/brief.py`). Исключение — ключевые слова и имена собственные (дословно). Заголовки страницы на языке GEO создаются на шаге 2 (`python -m textgen headings <run>` → `02_headings.json`, ключи в заголовках сохраняются: `heading_keywords`), шаг 3 их перепроверяет, шаг 4 собирает текст уже с локализованными заголовками.
- **В каждом ТЗ обязательна таблица с фактами о бренде** (как «Casino Information» на inca-spin.de): отдельный блок H2, формат `table`, **2-м или 3-м блоком страницы** (поле `fact_table` в блоке; схема и проверки — `validate_fact_table` в `textgen/brief.py`). Строки выбираются по таблицам конкурентов (`01_fact_tables.json`, шаг 1), значения берутся из базы знаний через `kb_refs` строки (дословно, код подставляет сам). Обязательные строки: licence, welcome_bonus, cashback, currencies, languages, payment_methods, support (e-mail); плюс company/founded/min_deposit и то, что есть у большинства конкурентов. Значения короткие (≤ 25 слов, без предложений; шаг 3 это проверяет в `check_fact_table`). E-mail поддержки содержит ключ (`support@incaspin.com`) — блок таблицы обязан заложить это вхождение в `keywords`. Без базы знаний таблицу построить нельзя: шаг 1 печатает предупреждение. Не копируй в таблицу цифры конкурентов (у inca-spin.de «до 2.500 €», старт «2026»): значения только из базы.
- Факты о бренде — только из базы знаний AffBulk (строка `Knowledge Base - <название>` во входном файле) и `facts`; в ТЗ и тексте ничего не выдумывать (лицензии, провайдеры, суммы).

## Типы страниц (`Page type`, `textgen/inputs.py`)
Правила выше и ниже описывают `brand-review` (по умолчанию, поведение не менялось). Два других типа включаются строкой `Page type - ...`; `validate(..., page_type, casinos)` в `brief.py`, промпты — `prompts/step1_brief_<тип>.md`, `step1_review_<тип>.md`, `writer_<тип>.md` (дописывается к системному промпту), `step3_consistency_<тип>.md` (`textgen/prompts.py`).
- `brand-subpage` (App, Login, VIP Program, Sports, Bonuses & Promo Code, Payments): `Brand - <имя>` обязателен (первый ключ называет тему и бренда не даёт). База знаний одна, но берётся нужная теме часть: ≥ половины блоков со ссылками (`validate_subpage_kb`), «все переменные использованы» и таблица фактов **не** требуются (`fact_table` запрещена). Обязательные кластеры конкурентов, не относящиеся к теме, пропускаются через `skipped_clusters` с причиной (не больше половины, `validate_skipped_clusters`). Остальное (ключи, размер, форматы, шаги 2–3) как у обзора.
- `top-list` («best/new/fast withdrawal/legal casinos», «Kasyna bez weryfikacji»): бренда нет (`brand_name == ""`), казино перечислены в `Casinos:` как `Имя | название базы AffBulk`, **порядок = рейтинг**. Шаг 0: для каждого казино найти базу (`knowledge_bases_find`) и сохранить в `runs/<run>/00_kb/<slug>.json` (тот же формат, что `00_knowledge_base.json`; ошибка шага 1 перечисляет все недостающие файлы сразу). `Run.knowledge_base()` склеивает их в одну базу, где ключи верхнего уровня — слаги (`kb.merge`), поэтому пути `kb_refs` начинаются со слага (`incaspin.brandinfo_welcome...`). Проверки (`validate_top_list`): у каждого казино свой раздел только с его фактами, разделы идут в порядке ввода, 2-м/3-м блоком H2 с таблицей сравнения, в `kb_refs` которой факты **каждого** казино. Таблицы фактов нет, оценок/«лучший»/«мы тестировали» нет — факты только из баз (см. `writer_top-list.md`). В запрос шага 1 базы идут сокращённо (`kb.digest`), в ТЗ подставляются полные значения.
- `Slug - <имя>` во входном файле задаёт папку запуска (по умолчанию `<первый ключ>-<geo>`, у подстраниц одного бренда и GEO он совпадает: без `Slug` шаг 1 откажется затирать чужой запуск). Пример: `input/longfu88-login-my.txt`, базовое ТЗ (группа medium: 844 → лимит 1013) строит `tools/longfu88/make_login_base.py`, 8 вариантов (3 small, 4 medium, 1 large) — `make_login_variants.py`.
- Варианты ТЗ (`variants`) работают с `brand-review` и `brand-subpage` (для подстраницы нет таблицы фактов, `skipped_clusters` наследуются от базы или задаются в варианте); для `top-list` cli отказывает. Импорт в AffBulk (`prompts/affbulk_import.md`, `affbulk/`): страница `index` бренда и подстраницы (`build_subpage`, раздел 9: **2 CTA**, ссылка на главную — **название бренда в тексте вступления**, отдельного абзаца нет; в ТЗ подстраницы у блока H1 автоматически стоит строка «Home link», `home_link_note`); для топ-листов правил импорта пока нет. `04_final.json` содержит `page_type`.
- Примеры ввода: `input/examples/`.

## Размер блока и ключи (правила шага 1–3)
- **Размерные группы и лимит страницы** (`textgen/tiers.py`, `01_tiers.json`, `python -m textgen tiers <run> --texts N`). Конкуренты (только страницы с текстом: пустые, `body_words == 0`, не считаются, `usable_pages`) делятся по естественным разрывам (два самых больших промежутка между длинами) на три группы: **small / medium / large**, например Login 238·385·524 | 844 | 1754. У группы: `target` = среднее группы, `limit` = среднее × 1,2 для small и medium и × 1,0 для large (`TEXTGEN_PAGE_LIMIT`, `TEXTGEN_PAGE_LIMIT_LARGE`). Конкурентов 2 → small, large и синтетическая medium (среднее двух), 1 → только medium; `--words` задаёт одну группу medium. **Базовое ТЗ строится по medium** (`targets.tier`, `target_body_words`, `max_body_words`, строка «Limit of the whole text» в `01_brief.md`). Малые тексты получаются урезанием базового ТЗ (самые важные блоки, 3 сущности и 1 связь на блок, мало фактов; «все переменные базы использованы» для small не требуется), большой — дополнением (блоки, которые есть у большого конкурента, +факты, 6 сущностей и 3 связи на блок). Варианты ТЗ называют группу полем `tier` чертежа (`variants.TIER_DEFAULTS`), лимит и цель берутся у группы; у large нижней границы суммы нет (текст может быть короче, если фактов не хватает), выше цели — нельзя. Распределение текстов (`tiers.allocate`): сначала medium, потом large (одиночный выброс — 1 текст на `TEXTGEN_LARGE_PER_TEXTS`=10 текстов, но не меньше одного), остаток: medium — большая половина, small — меньшая (8 текстов Login → 3 small, 4 medium, 1 large). Лимит проверяется: `validate` — сумма `words_max` блоков после расчёта под факты не больше лимита; шаг 3 — суммарный текст не больше лимита, иначе блоки, вышедшие за свой `words_max`, получают правку `page_limit`. Структуру страницы задают конкуренты (по блоку на кластер), факты наполняют её; расширять текст ради фактов нельзя: лишние факты и связи режутся, перечисления подаются коротким списком или таблицей.
- Размер блока: сначала `words_min/max` по конкурентам (LLM), затем код (`plan_budget` / `apply_coverage_budget` в `textgen/brief.py`, шаг 1.6) считает слова, которые нужны фактам и связям блока, и поднимает середину до этого числа (диапазон всегда середина ±12 %). Вес: каждая связь сущностей (`entity_connections`) — 15 слов (`TEXTGEN_WORDS_PER_CONNECTION`); **сущности (`entities`) слов не получают**; каждый пункт базы (`brand_info`) — по длине значения: слов значения × 1,2 (`TEXTGEN_FACT_TEXT_FACTOR`), минимум 3 слова (число, название), максимум 30 (`TEXTGEN_FACT_MAX_WORDS`); то, что блок показывает списком или таблицей, стоит слов самих пунктов (× 1,0, максимум 40). Блок только из таблицы и таблица фактов не раздуваются. Обе границы диапазона растут не более чем на +20 % от размера по конкурентам (`TEXTGEN_MAX_GROWTH`) и никогда не уменьшаются; блок, которому факты и связи нужны больше, чем разрешает рост (`need` > середина × 1,2), «перегружен»: `validate` возвращает ошибку «cut kb_refs and connections, or show enumerations in a list or a table». Пример: блок 53–67 слов с 7 фактами приветственного бонуса и 1 связью получает 60–76.
- Генерация может выйти за `words_max` на 10 % (`TEXTGEN_WORDS_OVERFLOW`; `block_cap`), минимум обязателен: вместе с ростом в ТЗ блок может вырасти максимум на ~30 %. Проверка размера в шаге 3 — только `< words_min` и `> cap`, плюс лимит всей страницы (см. выше).
- Приоритеты системного промпта: 1 стиль, 2 факты, 3 жёсткие ограничения ТЗ, 4 покрытие сущностей, 5 ценность для читателя.
- Ключи: падежные окончания и множественное число считаются (`count_keywords(..., inflect=True)` в шаге 3, до 3 букв к каждому слову); перевод и перестановка кодом не считаются. Название бренда (любое написание, в т. ч. внутри длинного ключа) при лимите 0 не проверяется и разрешено в тексте (`is_brand_keyword`); при лимите ≥ 1 счётчик по-прежнему точный. Бренд при лимите 0 — не чаще 1 раза на 50 слов (минимум 1; `brand_free_max` в `checks.py`, `TEXTGEN_BRAND_FREE_WORDS`).
- Шаг 2 пишет текст по разделам: H1 отдельно, каждый H2 вместе с вложенными H3 за один вызов (`sections`, `build_section_message`, ответ делится по строкам `=== bNN ===`, потерянный блок дописывается отдельным вызовом). Правки шага 3 идут по одному блоку. В каждый запрос уходит структура страницы с summary всех блоков.
- Таблицы и списки в ТЗ (`validate_visuals` в `brief.py`, правила в `prompts/step1_brief.md`): минимум — таблица фактов, таблица платежей (блок про оплату/депозиты), список шагов регистрации, таблица Pros and Cons (если такой блок есть). Маркированный список — равнозначные пункты, нумерованный — последовательность шагов, таблица — когда нужно 2+ атрибута на пункт; остальное проза.
- Связи сущностей: приоритет < 8 — цепочка subject → relation → object в одном предложении; 8–10 — отдельный короткий фрагмент (цепочка плюс факты, которые её поясняют).
- Связующий текст (переходы к соседним темам, практические советы вроде «проверьте условия») разрешён; запрет остался только на ссылки на источник факта («laut Plattform»).

## База знаний AffBulk (шаг 0 процесса)
Python не умеет вызывать MCP, поэтому базу достаёт Claude Code **до шага 1**:
1. Создать запуск: `python -m textgen step1 input/<файл>.txt --llm manual` (упадёт с подсказкой про базу знаний, папка `runs/<run>/` уже создана).
2. `mcp__…__knowledge_bases_find` с фильтром `{"title": {"$eq": "<название>"}}` (если не найдена — `$contains`, при нескольких совпадениях спросить пользователя).
3. Сохранить результат в `runs/<run>/00_knowledge_base.json`: `{"id", "title", "category", "variables": [{"key", "type", "value"}]}`; значения `json`-переменных можно оставить строками или разобрать в объекты, **содержимое не менять**.
4. ТЗ ссылается на данные путями (`kb_refs`, напр. `brandinfo_welcome.welcome_bonus.total_bonus`, `brandinfo_deposit.deposit_methods[0]`); код сам подставляет значения дословно в `brand_info` блока (`textgen/kb.py`). Не перепечатывать значения руками.
5. Проверки кода: каждый блок имеет ≥1 ссылку, все пути существуют, **каждая переменная базы использована хотя бы в одном блоке**.
6. Если в факте базы есть бренд/домен/e-mail («Incaspin Originals», `incaspin.com`), код добавляет «Counting warning»: такие слова считаются ключами, в `copywriter_notes` надо сказать, как перефразировать. Конфликты внутри базы («unresolved conflict», «previously recorded») обязательно разрешать в `copywriter_notes`.
- Без API-ключа LLM-части выполняются через `--llm manual` (запросы в `runs/<run>/llm/*.request.md`, ответы в `*.json`).
- Тесты: `python -m pytest tests` (не требуют API-ключа).

## Технические дубли (шингл 9) — проверка перед публикацией (правило пользователя, 2026-10-25)
- **Технический дубль** = 9 и более слов подряд, которые в том же порядке стоят в другом тексте (регистр, знаки препинания и разметка не считаются, числа вроде 2,088 — одно слово, слова идут подряд через границы предложений и ячеек таблицы; внутри блока). Тексты сайтов одного бренда и одной темы не должны делить такие отрезки: ни между вариантами, ни с текстами других типов страниц, ни с главными страницами этих сайтов.
- **Проверка обязательна перед записью в AffBulk**: `python -m textgen shingles 'longfu88-login-sg-v*' 'longfu88-bonus-sg-v*' 'longfu88-app-sg-v*' 'longfu88-sg-v*'` (аргументы — имена запусков или маски; берётся `04_final.json`; код выхода 1, если есть общие отрезки; `--show N` печатает первые N отрезков каждого текста, `--json` пишет полный отчёт). Код — `textgen/shingles.py`, тест — `tests/test_shingles.py`. Опубликованные главные страницы служат справочным корпусом: переписывается подстраница.
- Исправление: `tools/longfu88/dedupe.py report|apply <run> [<bNN> <файл>]` и `tools/longfu88/DEDUPE_GUIDE.md` (один запуск = один исполнитель; факты и числа остаются, формулировки свои; таблицы остаются таблицами, ключи и якоря ссылок сохраняются). Дословные цитаты из базы знаний в ТЗ («quote character for character») этому правилу уступают: числа и названия остаются, остальное пересказывается.
- **Белый список (защищённые факты)** (`textgen/protected.py`, правило пользователя 2026-10-25): названия акций и программ, имена, размеры бонусов, суммы, сроки, провайдеры, валюты, e-mail, лицензия — **дословные** значения базы знаний (короткие, не предложения; ≤ 12 слов) и бренд плюс явные имена из `data/paraphrase_banks/<база>.protected.txt`. В проверке шингла такая фраза считается **одним словом** (`§…`), поэтому само название или число дублем не бывает; слова вокруг него по-прежнему должны различаться. Названия не пересказываются и не переводятся. Отключить белый список можно флагом `shingles --no-protected`.
- **Как не получать дубли при написании (ТЗ → текст), всё в пайплайне:**
  1. *Карточки фактов* (`textgen/paraphrase.py`, `step2.prepare_cards`): в запрос шага 2 факт базы идёт не предложением, а карточкой — короткие значения дословно («keep exactly»), предложения заменены формулировкой из **банка пересказов** по слоту варианта (`slot_of`).
  2. *Банк пересказов* `data/paraphrase_banks/<база>.json`: 12 формулировок на каждое предложение базы (сохраняют числа и имена, ни одного общего 9-грамма с оригиналом и между собой). Команды: `python -m textgen bank list <run> [--chunk 25]` (пишет `<база>.requests/chunk_NN.json`), `bank check <run> --file <chunk_NN.answer.json>` (проверка ответа), `bank merge <run>` (сливает, печатает `retry.json` с ошибками), `bank status <run>`. `TEXTGEN_REQUIRE_BANK=1` — без полного банка шаг 2 не запускается; `TEXTGEN_PARAPHRASE_SLOTS` (12), `TEXTGEN_SHINGLE_N` (9).
  3. *Заметки, summary, связи уникальны на вариант*: после шага 1.8 каждый вариант переписывается своим голосом (`tools/longfu88/notes_diversify.py show|apply <run>`, ответ `llm/notes_div.json`; предложения, созданные кодом, и цифры сохраняются). Шлюз — `python -m textgen lexical <база>`: два ТЗ не делят 9 слов подряд (защищённые факты не считаются).
  4. *Раскладка фактов на вариант*: порядок равнозначных пунктов перемешивается по зерну варианта (упорядоченные ключи — нет), пара заголовков берётся по слоту (`HEADER_PAIRS`).
  5. *Список занятых оборотов* (`shingles.taken_phrases`, раздел `Phrases already taken` в запросе шага 2): обороты текстов-сестёр (`textgen/siblings.py`: тот же бренд, ГЕО, база, язык).
  6. *Проверка при записи*: `check_answer.py`, шаг 3 (`checks.check_shingles`) и `dedupe.py` сравнивают блок с сестринским корпусом с маской белого списка.
- Эталон «до»: 36 текстов SG (Bonuses/Login/App ×12) держали 54–64 % слов в общих отрезках, главные страницы SG ~74 %. Генерация шага 2 сама такие дубли не избегает: проверка нужна после шага 4 каждого набора вариантов.

## Импорт в AffBulk
Правила (сайт, набор и порядок блоков, наполнение, SEO, проверки, что сообщить пользователю) — в `prompts/affbulk_import.md`; читать перед каждым импортом.
Вход для импорта — `runs/<run>/04_final.json` (`blocks`: level, heading, text, formats; текст в markdown: абзацы, списки `- `, таблицы `| |`).
MCP-инструменты AffBulk доступны только внутри сессии Claude Code, поэтому запись выполняет Claude, а не Python-код.
Claude пишет `runs/<run>/05_affbulk_config.json` (website_id, SEO, hero, preview, отзывы, promo, при необходимости faq), затем `python -m affbulk.build_page <run>` собирает `05_affbulk_page.json` (порядок блоков и 5 CTA проверяются кодом) и после записи `python -m affbulk.verify_page <run> <readback.json>` сверяет страницу, прочитанную из AffBulk.
Все write-вызовы требуют `userAuthorized: true` только после явного подтверждения пользователя.


## Структура сайта: меню и внутренние ссылки (правила пользователя, 2026-10-25)
Полные правила — `prompts/affbulk_import.md`, раздел 10; код — `textgen/sitemap.py`, `affbulk/menu.py`, `affbulk/links.py`.
- **Header Menu:** новый пункт заменяет старый той же темы («Promotions» → «Bonuses»), а не добавляется рядом; в подвале аффилиатный аналог тоже заменяется внутренней ссылкой. Названия короткие, без бренда («Longfu88 Bonuses» → «Bonuses»). В шапке **не больше 6 пунктов**, остальное — в футер по тем же правилам, без лимита (`plan_menu`; при полной шапке последний аффилиатный пункт уходит в подвал, не оставляя в шапке меньше 3 аффилиатных). Писать в AffBulk только после показа пользователю результата `plan_menu`.
- **Анкоры внутренних ссылок — не больше 3 слов** («Longfu88 bonus for newly registered players» → «Longfu88 bonus»; «Longfu caino login» годится). Код: `wrap_phrase` отказывает, `check_anchors` входит в `check_page` / `check_subpage`.
- **Базовый набор страниц сайта типа Brand:** главная, bonuses, app, promo-code, login, no-deposit-bonus, payments (`BASE_SITE_PAGES`). Главная ссылается на все внутренние страницы; внутренние всегда ссылаются на главную; между собой — только если органично (регистрация упоминает промокоды → ссылка на promo-code). Разделы ради ссылок не создаются.
- **В брифе:** `Site pages - …` во входном файле (по умолчанию базовый набор без самой страницы; у top-list ссылок нет). Шаг 1 (1.7) расставляет страницы по блокам, где тема названа в заголовке или `summary` (`attach_internal_links`): в блок ТЗ и в запрос шага 2 попадает строка «Internal links» (обязательная у обзора, «optional» у подстраницы). Анкор писатель берёт из живого текста (≤ 3 слова), сборщик оборачивает его по конфигу `internal_links`. После записи — `site_link_report` по прочитанным страницам сайта.
- Уже собранные сайты Longfu88 (8 MY-сайтов) этим правилам не приведены, кроме longfu88-play.net: на остальных меню в старом виде (с брендом, больше 6 пунктов) и часть анкоров длиннее 3 слов — править по просьбе пользователя.

## Варианты ТЗ (шаг 1.8)
- Много текстов под одни вводные = один шаг 1 + `python -m textgen variants input/variants/<имя>.json` (чертёж: `textgen/variants.py`, в нём же сравнение вариантов). Каждый вариант — отдельная папка `runs/<база>-vNN/`; базовый запуск (`runs/<база>`) не трогать и не перезаписывать.
- **Структуры текстов должны отличаться всегда (требование пользователя).** Перестановка блоков, другие заголовки и склейка блоков структуру не меняют. Различаться должен и набор тем, и **глубина одной и той же темы** (раздел про приветственный бонус может быть одной строкой с номиналом, а может быть номинал + условия + как получить). Код это проверяет: `structure_distance` / `structure_conflicts` в `textgen/variants.py`. Расстояние между двумя вариантами = число тем, которые есть только у одного (по 1 за тему; блоки базового ТЗ и новые блоки по заголовку) + сумма различий глубины по общим темам (до 1 за тему: факты базы 0,4 — доля непересекающихся `kb_refs` темы, формат 0,25, размер 0,25 — разница середины диапазона, 40 % и больше = полностью, уровень H2/H3 0,1; склеенный блок делит размер между своими темами и сравнивается только своими фактами темы). Любая пара обязана набрать `TEXTGEN_MIN_STRUCT_DISTANCE` (по умолчанию 2,0); иначе `python -m textgen variants|compare` печатает «STRUCTURE TOO SIMILAR», таблицу «Structure distance» (какие общие темы отличаются сильнее всего) пишет в `output/<база>-variants.md` и завершается с кодом 1 (обход: `--allow-similar`, только по явной просьбе). Глубину темы в чертеже задают `refs_add`/`refs_drop` (какие факты базы берёт блок), `fmt`, `words` и текстом `extra`/`notes`: у одного варианта «только номинал» (1–2 факта, 30–45 слов), у другого «номинал, условия, как получить» (6–8 фактов, список или таблица, 100+ слов). Как закладывать при написании чертежа: ещё до чертежа составить пул тем (блоки базового ТЗ + 3–6 необязательных тем, которые базе знаний по силам: игры/спорт/оплата/бонус/регистрация/ответственная игра/сравнение/глоссарий и т. п. в зависимости от страницы), затем каждому варианту раздать свой набор: часть обязательных кластеров у разных вариантов опускается (в пределах `skipped_clusters` ≤ половины), часть необязательных тем есть только у одного-двух вариантов, а не у всех; медиум-варианты тоже различаются составом, не только порядком. Если база знаний по теме бедная (как у App: пара абзацев), необязательные темы берутся из соседних разделов базы (платежи, бонусы, спорт, игры), 1–2 коротких блока, не больше.
- Чертёж пишет Claude (он же «LLM» этого шага): уникальные заголовки (в вариантах нет общих), свой порядок и состав блоков, разные форматы, размер, голос страницы, примеры игр/провайдеров, вопросы FAQ. Факты и решения конфликтов (6000/5000 игр, промокод, Bronze–Platinum, рассрочки, злотый, «не лицензировано в Польше») наследуются из заметок базового ТЗ — в `notes`-переопределениях их надо повторять вручную.
- Текст про число ключей в `copywriter_notes` код создаёт сам; в чертеже его не писать. Блоки с дословными значениями базы, где есть ключ (`INTRINSIC` в `variants.py`: e-mail, шаги установки PWA), имеют минимальное число вхождений.
- Для бренда не Incaspin чертёж несёт собственные правила верхнего уровня: `intrinsic` (по id базового блока: ключ, минимум вхождений, `replace`/`drop_prefix` для фраз о счёте в заметках — e-mail в таблице фактов и в блоке поддержки, шаги установки), `brand_names` (что вырезать из заголовков в заметках склеенных блоков), `keyword_labels`. Без них действуют значения для Incaspin (`textgen/variants.configure`). Пример: `input/variants/longfu88-sg.json` (+ генераторы в `tools/longfu88/`: `make_base.py` — ответ шага 1 в ручном режиме, `make_variants.py` — чертежи; запускать из корня проекта).
- Longfu88: варианты собирались с `TEXTGEN_MAX_GROWTH=0.45` (при 0,25 диапазоны блоков с длинными заметками оказывались меньше нужного: текст приходилось резать). Это про старые обзорные варианты (рост тогда был 25 %); с правилами выше (рост 20 %, лимит страницы) `TEXTGEN_MAX_GROWTH=0.45` для новых запусков не нужен.
- Ручной режим (без API): шаги 2–4 для запуска выполняются по `tools/longfu88/WRITER_GUIDE.md` (помощники `next_request.py`, `check_answer.py`, `apply_fix.py` в той же папке); один запуск = один агент.
- Если базовое ТЗ пересобрано (`step1 --force`), варианты пересобрать (`variants … --force`): `clean_notes` упадёт с ошибкой, если заметки базы изменились так, что правки (`edit`) больше не находят текст.
